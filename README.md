# Детекция камней на доске Го

Проект реализует пайплайн подготовки данных, обучение детектора (YOLOv5), экспорт в ONNX и минимальную веб‑обёртку для продакшн‑проверки. Модель детектирует камни и пустые пересечения, возвращая bbox + класс + confidence и карту \(19\times19\) для восстановления позиции.

---

## Описание проекта

**Цель**  
Определять наличие и цвет камня в каждой ячейке фиксированной сетки доски Го (по умолчанию \(19\times19\)). Результат — карта клеток с метками и confidence, пригодная для восстановления позиции на доске и дальнейшей логики игры/анализа.

**Ключевые этапы**  
- Подготовка и проверка аннотаций (Roboflow / YOLO формат).  
- Обучение детектора YOLOv5 на ваших данных.  
- Экспорт лучшего чекпоинта в ONNX для inference.  
- Разработка FastAPI‑сервиса, который: ресайзит изображение, прогоняет ONNX, выполняет декодирование + NMS, маппит bbox → 19×19 и возвращает JSON / аннотированное изображение.  
- Валидация качества (mAP, precision, recall) и per‑cell accuracy (маппинг bbox → ячейка).

## Использованные инструменты и почему

**Язык и фреймворки**
- **PyTorch / YOLOv5** — проверенная реализация детекции, простота обучения и экспорт в ONNX.  
- **onnxruntime** — быстрый и переносимый inference в контейнере (CPU).  
- **FastAPI + Uvicorn** — лёгкая и быстрая веб‑обёртка для демонстрации и тестирования.

**Подготовка данных**
- **Roboflow / ручная разметка** — экспорт в YOLO формат (images + labels).  
- **Pillow, NumPy** — чтение/обработка изображений и постобработка bbox.

**Аугментации и баланс**
- **albumentations** (опционально) — реалистичные аугментации (яркость, контраст, повороты, шум).  
- **Аннотации** — аккуратные bbox важны для mAP при высоких IoU.

**Метрики и анализ**
- **pycocotools / yolov5 val.py** — mAP@0.5, mAP@0.5:0.95, precision, recall.  
- **scikit‑learn** — confusion matrix и дополнительные метрики по ячейкам (если маппим bbox → grid).

**Деплой**
- **Docker** — контейнеризация сервиса с onnxruntime и FastAPI.

## Метод и теория

**Подход — детектор (YOLO) + маппинг на сетку**
1. Детектор на входе получает изображение, ресайзится до \(640\times640\) (как при обучении).  
2. YOLO предсказывает набор bbox с классами и confidence.  
3. Выполняется NMS для удаления дубликатов.  
4. Для каждой bbox вычисляется центр и маппится на ячейку \(19\times19\) (по центру bbox → индекс ячейки).  
5. При конфликте (несколько bbox в одной ячейке) выбирается bbox с наибольшим score.  
6. Возвращается карта 19×19 и список детекций (bbox, score, class).

**Почему детектор**
- Детектор даёт более точную локализацию и лучше справляется с плотными или частично перекрывающимися камнями.  
- mAP50 показывает практическую пригодность для задачи «есть/нет камня в ячейке», а mAP50‑95 отражает качество локализации при строгих IoU.

## Результаты эксперимента (ключевые логи и метрики)

**Окружение**  
- Device: GPU (обучение) / CPU (контейнер с onnxruntime)  
- YOLOv5s backbone, экспорт в ONNX (opset 12)

**Ключевой лог (пример вывода val.py)**  
```
Model summary: 157 layers, 7018216 parameters, 0 gradients, 15.8 GFLOPs
                 Class     Images  Instances          P          R      mAP50   mAP50-95
                   all        200      36658      0.978      0.952      0.973       0.71
                 empty        200      18280      0.974      0.919      0.959      0.625
                 black        200        200      0.996          1      0.995      0.872
```

**Интерпретация**  
- **mAP50 = 0.973** — отличная практическая точность при IoU=0.5.  
- **Precision ≈ 0.98, Recall ≈ 0.95** — мало ложных срабатываний и большинство камней обнаружено.  
- **mAP50‑95 = 0.71** — при более строгих IoU локализация хуже, что указывает на возможность улучшить точность боксов (аннотации, postprocessing).

**Per‑cell accuracy (пример)**  
- После маппинга bbox → 19×19 итоговая точность восстановления позиции ≈ **0.95** (зависит от правил агрегации и порогов).

## Практическая демонстрация и команды

### Подготовка данных
Структура `yolo_data`:
```
yolo_data/
  data.yaml
  names.yaml (или names в data.yaml)
  train/images/*.jpg
  train/labels/*.txt
  val/images/*.jpg
  val/labels/*.txt
  test/images/*.jpg
  test/labels/*.txt
```

```yaml
train: /path/to/Go-Positions-6/train/images
val:   /path/to/Go-Positions-6/valid/images
test:  /path/to/Go-Positions-6/test/images
names: ['empty','black','white']
```

### Запуск веб‑сервиса (Docker)
```bash

docker build -t onnx-quick-check .

# запустить контейнер с моделью
docker run -d --name onnx-quick -p 8000:8000 \
  -v $(pwd)/app/model:/app/app/model:ro \
  -e MODEL_PATH=/app/app/model/model.onnx \
  onnx-quick-check

```

```bash

curl -X POST "http://localhost:8000/predict_image" -F "file=@/path/to/test.jpg" --output annotated.png
```

## Постобработка: bbox → 19×19 (пример логики)
1. Для каждого bbox вычислить центр \((cx,cy)\).  
2. Нормировать координаты в пикселях относительно исходного размера (если модель работала на 640×640 — масштабировать обратно).  
3. Индекс ячейки:
   \[
   gx = \min(GRID\_N-1, \left\lfloor \frac{cx}{W/GRID\_N} \right\rfloor),\quad
   gy = \min(GRID\_N-1, \left\lfloor \frac{cy}{H/GRID\_N} \right\rfloor)
   \]
4. При конфликте (несколько bbox в одной ячейке) — выбрать bbox с наибольшим score.  
5. Вернуть `grid[gy,gx] = class`.

## Заключение

Использование YOLO + ONNX даёт надёжный и быстрый пайплайн для распознавания позиций на доске Го. Текущая модель демонстрирует **высокую практическую точность (mAP50 ≈ 0.973)** и хорошую полноту/точность для задач восстановления позиции по сетке. Для повышения точности локализации и устойчивости к реальным условиям стоит улучшить аннотации, усилить аугментации и рассмотреть гибридные архитектуры (детектор + сегментация).
